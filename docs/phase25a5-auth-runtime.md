# Phase 25A.5: request-time authentication and safe logging

Observed on protected Production: a session lookup on `/messages` failed with Next.js `HANGING_PROMISE_REJECTION`, while HTTP responses and realtime delivery could still succeed. Better Auth emitted raw SQL parameters. Treat logged session tokens as potentially exposed; never copy raw logs into tickets, chats, or this repository.

This patch adds a request-time `connection()` boundary before header retrieval and the existing provider-error catch. It leaves Cache Components, partial prefetching, account authorization, session deduplication, and the Neon/Redis topology intact. The Better Auth logger discards message and argument data and maps only warn/error levels to bounded fixed events. The underlying failure still has to be resolved, not merely hidden. No schema, environment, dependency, frontend, or auth endpoint changes.

Offline regression tests simulate request boundary rejection, anonymous and successful sessions, provider failure and logging with synthetic secrets. They do not prove framework integration or live behavior. Run full CI, exact migrations, build, protected Preview navigation and protected Production acceptance. Verify `/messages` on direct navigation, in-app links, prefetch and refresh; check authentication, role gates, session expiry/logout, and Production WebSocket delivery across the lease. Review logs for both the old raw errors and new `auth_internal_error`, `auth_internal_warning`, `session_lookup_failed` events. An unexplained new event remains a blocker. Never publish raw logs. Compare resource counters without new load tests.

Incident response: keep deployment protection on; restrict runtime log access and review retention/deletion options. Revoke potentially exposed sessions (including older sessions and sessions created before the fixed deployment), not credentials or users. In this prelaunch environment a coordinated all-session revocation is reasonable if explicitly approved and the exact Production database is verified. See external bundle runbook. Old deployments may still contain vulnerable code: retire or restrict them. Existing WebSockets check authorization before sending relay notices and have a bounded lease; do not claim instantaneous closure. No automatic production mutation or deployment is part of this patch.
