# Phase 21F/G: targeted page-read optimization

Baseline: 100 distinct authenticated Preview members, three waves / 300 HTTP reads, 300 success; p50 1172 ms, p95 2289 ms, max 3190 ms. Dashboard p50 999 ms, directory p50 1265 ms. This was not sustained traffic or WebSocket load. Prior resource screenshots were cumulative and lagged.

## Changes and boundaries
- `vercel.json` sets `regions: ["fra1"]` for future deployments. Frankfurt matches the observed Neon and Redis regions. Verify the actual execution region on an invocation in the new Preview logs. The old function region is unknown. No existing deployment changes.
- React `cache` shares the page-account loader within one server render only. No persistent cache, Redis cache, cookie-cache or authorization TTL. The layout and dashboard/directory/profile/member-detail use the same page helper. Every separate render still reads the authenticated session and account state. All API and mutation helpers remain uncached; messaging services unchanged. The existing Suspense/static shell boundary remains intact.
- Established page accounts use a single primary-key join for account state and profile; missing rows or UNVERIFIED use the original initialization/transition loader. Database failures propagate and never authorize by default. The directory still enforces its existing per-user Redis rate limit and ACTIVE row filter. No schema/index changes or public/shared member data cache.
- Optional `IMS_PHASE21_PROFILE=true` (Preview only): independently samples 10% of stage calls, with at most 30 sampled stages per minute per warm instance. Fixed labels only; no IDs, paths, credentials or query inputs. Stages: session, account_join, account_fallback, directory_limit, directory_query. Sampled wall times are not full HTTP latency; samples are not correlated by request. No new service, timer, or Redis operations. Disable flag for clean benchmarks and compare same deployment settings apart from the intended code change.
