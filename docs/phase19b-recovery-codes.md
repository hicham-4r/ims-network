# Phase 19B: member recovery codes (gated)

## Scope
- One 256-bit single-use recovery code per ACTIVE MEMBER with an unverified email; no owner or administrator recovery through this mechanism. A new code replaces the old one. Expires in 365 days; a changed password hash or account-state version invalidates it. The user must generate and save a code before losing access. No recovery is guaranteed without it. Previously verified accounts retain the legacy email flow.
- No database schema migration or provider subscription. Uses the existing indexed `verification` table, with an application-specific `ims-recovery-v1:` ID and identifier prefix; the identifier is an HMAC of the random code and the value is a separate keyed binding to user, credential and account-state version. Better Auth's existing verification identifiers are untouched. Secret rotation invalidates all codes. Expired records are eligible for Phase 19A cleanup.
- Password reauthentication for issuance, strict origin/JSON/body checks, 5 attempts per 10 minutes by IP and by account for issuance, 5 per IP for redemption, fail-closed Redis, Turnstile on redemption. Never send codes by email, place them in URLs or store them in browser storage. Existing role/status remains unchanged. Audit events have no code or credential content.
- The existing configured Better Auth password hash/verify functions are used. SQL checks the credential and state under locks, consumes the exact record and changes password/revokes existing sessions/inserts an audit event atomically. The current session cookie becomes unusable after revocation. Existing in-flight sign-in or WebSocket races must be tested in Preview; this patch does not change session creation or socket lifetime rules.

## Enable only on protected, isolated Preview for validation
Default is OFF. Set `IMS_RECOVERY_CODES_ENABLED=true` for Preview only (Config); set it in both runtime and build if using a CLI deployment override. Never enable on Production until live SQL and compatibility checks pass. Keep existing Turnstile configuration, Redis, Neon and owner variables. Retire obsolete Preview builds sharing the test database before testing security mutations. No migration needed.

## Acceptance on disposable, approved ordinary account
1. With flag unset, GET/POST recovery endpoint cannot mutate records; app indicates unavailable. Verify admin/owner and pending/suspended members cannot issue a code, even by calling POST directly. Verify wrong password, missing session, cross-origin request, malformed/oversized body and limiter outage are rejected.
2. Enable flag on protected Preview. Sign in as controlled unverified ACTIVE MEMBER. Open `/account-recovery`; enter wrong password (rejected), then correct password. Save code privately. Generate another and confirm the first is invalid. Check only one namespaced record per account, with digests not plaintext (do not print credential data). Admin audit shows issuance only, no secret.
3. Use a separate browser to open `/recover-with-code` via forgot-password. Enter an invalid code (generic error), then the latest code and a new password, completing Turnstile. Confirm old password fails, new password works, previous browser session is invalid, account remains ACTIVE MEMBER, messages remain. Verify reused code fails. Check audit event.
4. Test simultaneous redemption in separate browser profiles with distinct CAPTCHA tokens (one successful reset maximum), rotation vs redemption, and suspension/promotion vs redemption on disposable accounts. Confirm old code cannot reset an account after status/role changes even after restoration/demotion. Confirm expired records are rejected. Do not expose any secrets in screenshots/logs. Confirm old sessions cannot read protected routes and assess concurrent in-flight sign-in and existing sockets against current revocation policy. Verify database atomicity on transaction failures in isolated database.
5. Confirm normal sign-in, registration/admin approval, role changes, previously verified reset behavior, admin audit pagination, and messaging remain working. Real Turnstile test and resource measurements remain release gates.

## Rollback
Unset flag and redeploy, or revert the guarded patch. Issued codes become unusable while disabled; to permanently invalidate all previously issued codes, rotate the auth secret as part of a planned session-impacting change or explicitly delete the namespaced records from the isolated database after review. No automatic data deletion or migrations by installer. Do not run broad DELETE on verification.
