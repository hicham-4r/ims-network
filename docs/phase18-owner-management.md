# Phase 18A+B — Turnstile and owner-managed administrators

## Ownership setup (no database migration)
OWNER is a server-only effective permission tier. The configured immutable `IMS_OWNER_USER_ID` must match an existing ACTIVE ADMIN row in the current database. Database role stays ADMIN, so all existing member/admin guards still apply. Missing, malformed or unmatched configuration grants no owner privileges. There is no automatic bootstrap from email, first user, or first admin; no public endpoint can set ownership. Configuration changes are operator-controlled and require a fresh deployment. Existing admin keeps all access before and after setup. Other admins do not inherit ownership. This intentionally avoids adding an enum migration or overwriting an account.

1. On the already-working protected Phase 17 Preview, sign in with your existing admin. Open `/admin/accounts?status=ACTIVE`; find your own account and open **Account details**. Confirm status ACTIVE and role ADMIN. Copy **User ID** (not email, cookie or session ID). Do not send it to chat. If using a different database, repeat identification in that environment. For local dev use its matching ID in `.env.local` if needed; never commit that file.
2. Vercel project Settings → Environment Variables: add `IMS_OWNER_USER_ID` with exactly that ID, Preview only for now. No `NEXT_PUBLIC_` prefix. Ensure this deployment uses the same isolated Preview Neon database. If a future Production database has a different account ID, configure separately after verifying the existing admin there. Never copy Preview credentials or dummy Turnstile keys to Production. Do not change Production today.
3. Set Turnstile variables as described in `phase18-security-hardening.md`. For protected Preview only the official dummy always-pass keys can be used; real keys must be tested before launch. `IMS_TURNSTILE_TEST_MODE=true` for dummy testing only. Keep relay disabled during this trial. Redis must be available for owner mutations, even locally. No changes to existing database URLs.
4. Deploy new Preview; confirm `/admin` says Your role: OWNER for your existing account. If it says ADMIN, fix configuration, do NOT create a new owner or promote a different account. Retire obsolete Preview deployments sharing this database before using role management; old builds do not implement the new mutation locking. Do not leave multiple owner configurations active against one DB. Owner recovery/transfer is an operator-only deployment configuration change; application has no transfer or delete-owner feature.

## Role management
Owner only: select another ACTIVE MEMBER in Account details, enter your current password, check confirmation, promote. To remove admin access use the same page. The database checks actor ADMIN/ACTIVE, matching configured ID, current session, target ID, expected role and status, with actor/session locks. Target session revocation and audit insertion occur atomically with role update. Never log password or raw exceptions. Rate limiter: 5 attempts per 10 minutes per authenticated owner, fail closed; ordinary navigation adds no Redis calls. Existing admin/member account-state transitions still work. To suspend an administrator, owner must first demote, then suspend the member with existing controls; both operations audit separately. No self/owner role changes. No additional access to private messages. Open sockets may survive until the existing bounded lease/revalidation; role changes do not grant socket admin abilities. Old session cookies cannot authorize new admin requests after revocation. Audit viewer shows only allowlisted role/status transitions, not raw metadata.

## Protected Preview acceptance (not run by installer)
- Existing owner remains ACTIVE, sees OWNER; a normal admin sees ADMIN, not role forms. No configured ID => no role changes, ordinary admin moderation still works.
- Pending/suspended/rejected member cannot be promoted. Owner cannot be demoted or suspended. Incorrect password or missing confirmation causes no role/audit mutation. Verify direct crafted server-action requests from member/non-owner admin are denied. Rate limit or unavailable Redis denies mutation. Do not share secrets or replay actual password-bearing requests in screenshots.
- Promote controlled active test member, verify role grant audit, old session denied; sign in again and approve a separate pending test account as new admin. Verify they cannot promote or demote, suspend owner, or view unrelated private messages. Owner demotes them, audit records revoke, old admin session denied, member login still works. Verify no duplicate role audit on repeated identical operation. Exercise concurrent demotion vs account moderation and confirm stale admin cannot mutate after demotion commits. Do not use real members for destructive tests.
- Retest sign-up, pending approval, CAPTCHA, dashboard, messaging, privacy and audit filtering. Record actual usage. No automatic migrations, commits, deployment or environment changes in installer.

## Remaining launch gates
Password reset delivery and mailbox ownership remain limited by the no-email-verification decision; independently verify any privileged user's identity and control of their mailbox before promotion. Never grant admin to an untrusted/spoofed address. Recovery redesign, real CAPTCHA keys, dependency audit, CSP, live concurrency and authorization tests, and free-tier resource measurements remain open.
