# Phase 25B.5 — authenticated password change and public landing page

The existing Privacy & security settings page (`/account-privacy`) now offers an independent Account & Security panel for ACTIVE members and the owner. The public page removes the milestone card, its disclaimer, Roadmap section and link. The original left-aligned hero width, CTAs, remaining sections, footer and theme stay intact.

## Security contract

- `POST /api/auth/password-change` is application-owned and intercepted before the Better Auth handler. The generic framework `/change-password`, `/set-password` and session management endpoints remain blocked. Exact path, canonical origin, JSON content type and 16 KiB bounded body protections are inherited from the existing auth boundary. Queries and unknown fields (including target IDs) are rejected.
- Dedicated fail-closed 5-attempt/10-minute fixed-window counters per trusted IP and authenticated account. Preview uses the existing isolated PostgreSQL limiter; Production uses dedicated Redis. No Turnstile on this authenticated mutation; current credentials and active session are required.
- Existing password length policy: 8–128 characters; recommend a unique long password. Current password verified using the configured Better Auth hasher; equivalent new passwords rejected. The new hash uses that same hasher. No password, hash, token or provider exception is logged or returned. No email verification or recovery flag required.
- Read the one credential and live session, verify password, then under PostgreSQL locks recheck ACTIVE state/version, old credential hash, live session and ownership. The password update, existing recovery-code record deletion, all stored sessions for that user (including current), and minimal PASSWORD_CHANGED audit event are in one transaction. A failed comparison or lock/statement timeout fails closed. No state, role, owner, profile, other-account or schema changes. The old recovery code is invalid; eligible members must generate a fresh one when enabled. Existing verified-email reset flow and pending reset-token lifetime are unchanged.
- Full document navigation to sign-in after success. A nonsecret informational query marker is not proof of password change or authorization. Disabled session cookie cache means deleted session rows are not accepted. WebSocket access uses the existing per-outbound-notice check and bounded lifetime, not immediate cross-instance disconnect; no new polling. In-flight authorized operations and already rendered client content are not retroactively withdrawn. Concurrent native sign-in/reset operations retain their pre-existing semantics; no claim of serialization of all Better Auth endpoints. Verify race cases in isolated Preview before release.

## Validation and acceptance

`node tools/ci/validate.cjs`, `node tools/ci/check-migrations.cjs --exact`, `git diff --check`, `npm run build` (reviewed local non-Production environment). Existing and new offline suites are not a replacement for a real PostgreSQL/Better Auth runtime test. The new CJS test exercises mocked route/service modules, validates input, authorization and limiter failures, observes SQL parameterization/structure and checks landing JSX; it does not prove transaction locking, React rendering or cookie/session behavior.

Protected Preview first (own database, no Redis or relay); use synthetic accounts, never share credentials or tokens. Test two browser profiles for the same member, another unrelated account, and a restricted account. Start with valid change; old credentials fail, new work, both old sessions are denied after refresh, other member unchanged. Test wrong current, weak/mismatched/no-op passwords, unknown target ID, anonymous and pending/suspended requests, missing/wrong Origin, noncanonical paths, oversized body and throttle. IP/account budget is only five attempts per ten minutes, so space negative checks or use isolated fixture tests for boundary cases; don't bypass/disable rate limits. Verify exactly one audit event per successful change, no sensitive logs, account status/role unchanged. Test competing password changes and recovery issuance/redemption where enabled in an isolated non-Production environment; do not weaken owner email recovery or turn on Production flags early. If provider or test timing prevents any checks, record them as unverified.

Review desktop/mobile and zoom, keyboard focus, password-manager autocomplete and show/hide, both themes, absence of removed blocks, working sign-in/signup/privacy anchors, exact hero alignment. Production must remain protected; deploy only reviewed main and after approval. Repeat bounded synthetic success and security checks, confirm current and other sessions revoked, and old credentials fail. Confirm owner fallback before testing owner change (avoid unnecessary repeated changes). Recovery-code invalidation live check when enabled in Phase 25C. Test revoked messaging session on delivery and reconnect, review sanitized logs, usage and quotas. No new subscriptions, migrations or background requests. Preserve the three disabled flags until authorized. Test-account cleanup and release of emails remain a later, separately approved Phase 25D operation.
